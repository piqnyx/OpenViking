# OpenViking: наша ветка

Форк `piqnyx/OpenViking`, ветка `piqnyx/0.4.12` от тега `v0.4.12` (коммит `c1d38eb4`). Версия сервера
зафиксирована, обновляться решено не было. На сервере gate-de до нашей сборки стоит чужой образ
`ghcr.io/volcengine/openviking@sha256:0d99361a0029ce5221fd11588d9f0f374c6e5f8f1eacbcf1d76de6a0f6cd82cb`,
внутри тот же код: `session/session.py` и `utils/model_retry.py` совпадают с тегом байт в байт
(проверено 29.09.2026 отпечатками в контейнере).

Здесь записывается, что решено, что измерено и что сделано. Правило попадает в код, только когда
измерено; замер пишется сюда сразу.

## Цель (слова Вита, 29.09.2026)

«Наша задача сейчас сделать стабильным всё это, чтоб такого не повторялось, чтоб контекст не терялся
даже не смотря на шторма». «Чтоб ошибки от шторма 503, 400, 403, 401, обрывы не мешали Викингу в
конце концов когда-то да закончить всё, что он хотел сделать. Вот у графити оно именно так: висит,
повторяет до победы, ещё и лесенки там есть, бэкоф по времени». «Это продукт, и он должен работать
без постоянного обращения к тебе и расследований».

Образец -- наш graphiti, `mcp_server/src/piqnyx_reliable_queue.py`: сорванная задача повторяется на
месте, пауза растёт с 2 с до 900 с, состояния «сдался» нет, следующие задачи её не обгоняют.

## Случай 28.09.2026

Шторм 503 у Гугла с 14 до 18 часов (время сервера), 61 отказ. Коммит сессии чата в 17:32:04,
извлечение шло через прокси на `gemini-3.5-flash-lite` запросами по 574 КБ (~119 тыс. токенов) и
получало 503 по всей лесенке моделей. В 17:39:17 архив `archive_037` помечен сорванным. После этого
сервер перестал отдавать пересказ, плагин отдал шлюзу всю переписку (1117 сообщений, 377 тыс.
токенов), прокси отказал, чат встал. Плагин исправлен отдельно (PR 43–45 в
`piqnyx/openviking-openclaw-plugin`), чат ожил 29.09 в 09:06. Сервер остался как был.

## Что известно (проверено: чем)

### Как сервер повторяет сейчас -- код `v0.4.12`

- Один вызов модели: `openviking/models/vlm/backends/openai_vlm.py`, `retry_async` с
  `max_retries = vlm.max_retries` (по умолчанию 3), пауза от 0,5 до 8 с.
- Шаг извлечения: `session.py`, `_run_retryable_phase2_step` -- ещё 3 повтора, пауза 1–8 с
  (`_MEMORY_EXTRACTION_MAX_RETRIES`, константы, в `ov.conf` их нет).
- Итого до 4 × 4 = 16 вызовов на шаг. 28.09 это заняло семь минут, шторм шёл четыре часа.
- Оба слоя повторяют только класс `transient` (`is_retryable_api_error`).
- Дальше `_run_memory_extraction` пишет `.failed.json`, задача в Task Center -- Failed. Сам сервер к
  архиву не возвращается. Следующий коммит склеивает сообщения всех сорванных архивов с текущими
  (`_prepare_phase2_archive_messages`): запрос растёт.
- Шагов три, идут одновременно: пересказ (`archive_summary`), долгая память (`long_term`), память
  исполнения (`execution`). Успешные шаги памяти записываются в `.meta.json` архива
  (`completed_memory_steps`) и при повторе не делаются заново. Пересказ при успехе пишет
  `.overview.md` сразу -- поэтому у сорванного `archive_037` пересказ на диске лежит.

### Что сервер отдаёт как контекст -- код, `_collect_session_context_components`

Архивы просматриваются от нового к старому до первого с меткой:

| Самый новый архив с меткой | Пересказ | Сообщения |
|---|---|---|
| закрыт (`.done`) | его | висящих архивов новее него и активные |
| сорван (`.failed.json`) | НЕТ | только висящих новее него и активные |

Висящий архив (без метки) свои сообщения отдаёт целиком. Значит, пока архив повторяется и висит,
контекст полный: прошлый пересказ плюс его сообщения. Теряется контекст только от метки «сорван».

### Очередь -- код

- Извлечение идёт через очередь на диске: `queuefs`, по умолчанию `sqlite`. При старте все задачи,
  бывшие в работе, возвращаются в очередь (`recover_stale_sec = 0` -- вернуть все).
- Задача снимается с очереди, только когда обработчик кончил без исключения
  (`queue_manager.py`, `process_one`). `_run_memory_extraction` исключений наружу не выпускает.
- Рабочих мест у очереди коммитов четыре (`max_concurrent_external_parse`), на все сессии и всех
  агентов.
- Следующий архив той же сессии ждёт, пока все прежние получат метку
  (`_wait_for_previous_archive_done`, опрос раз в 0,1 с, без срока). Ждущий занимает рабочее место.

Способов два, и дают они разное.

**Из корня форка.** Пакет берётся из каталога исходников, родных библиотек в нём нет. Тесты на
подделках идут, тесты на настоящем хранилище нет: 42 ошибки «Rust binding not available» и на

## Сборка образа (этап 2)

### Решение

Образ тонкий: берётся ровно тот образ, что работает, по отпечатку, и поверх кладутся наши файлы.
Полная сборка из исходников тянет компиляцию Rust и даёт другие родные библиотеки, чем работают
сейчас; для правки в двух файлах Python это лишний риск.

Имя `piqnyx/openviking:0.4.12-piqnyx.1`. В реестр образ не уходит, живёт на диске сервера.

### Что где лежит

| Файл в `piqnyx/` | Что делает |
|---|---|
| `image.conf` | факты сборки: тег, образ-основа по отпечатку, где в нём пакеты, пользователь сервера, имя и версия нашего образа |
| `overlay.txt` | список наших файлов, по одному в строке |
| `Dockerfile` | основа и один шаг поверх неё |
| `lay_over.sh` | этот шаг: кладёт файлы списка по местам и собирает их байткод |
| `build.sh` | сборка; контейнеры не трогает |
| `check_list.py` | сверяет список с разницей ветки и тега |
| `verify-image.sh` | проверка собранного образа; контейнеры и данные не трогает |
| `compare_images.py` | сверка двух образов по файлам |
| `inside_check.py` | проверка изнутри образа от пользователя сервера |
| `test-in-image.sh` | тесты внутри старого образа и нашего, сравнение двух прогонов |
| `tests-inside.txt` | какие тесты исходника гонять: те, что говорят о коммите сессии, архивах и задачах |
| `test-ov.conf` | выдуманный конфиг для тестов: модель по адресу, где никто не слушает |
| `run_tests_inside.py` | прогон внутри образа: что стало с каждым тестом, по записи на тест |
| `compare_runs.py` | сравнение двух прогонов |
| `replace-container.sh` | замена контейнера с проверками до неё и возвратом прежнего, если новый не поднялся |
| `edit_compose.py` | правка compose-файла: строка образа и `pull_policy: never`, больше ничего |
| `pending_archives.py` | нет ли архива сессии в работе: читает только имена каталогов и меток |

Тесты: `python3 -m pytest piqnyx/tests -q -p no:cacheprovider -o addopts=""` из корня форка. Нужен
только pytest; один тест из 179 пропускается, если нет pytest-timeout.

### Что сборка проверяет до сборки

- В каталогах `openviking`, `openviking_cli`, `piqnyx` нет незакоммиченного: образ собирается из
  коммита, номер коммита пишется в метку образа `org.piqnyx.commit`.
- Список равен разнице ветки с тегом: каждый изменённый или новый файл двух пакетов в списке есть,
  лишних имён в списке нет.
- Не изменено то, чего рецепт в образ не кладёт: точка входа, родные библиотеки, зависимости. Убранный
  файл наложением не сделать, он тоже останавливает сборку.
- Основа лежит на диске; сети у сборки нет (`--network none`).
- Версию, на которой уже работает контейнер, сборка заново не собирает: новая сборка -- новая
  строка `VERSION`.

### Что проверка проверяет после сборки

Оба образа читаются в своих разовых контейнерах, без сети и без подключённых каталогов.

| Вопрос | Чем отвечает |
|---|---|
| изменились только наши файлы | отпечаток, права и владелец каждого файла обоих образов |
| наши файлы те, что в коммите | отпечаток файла в образе против файла в каталоге |
| основа равна тегу | все файлы двух пакетов из тега против основы |
| образ стартует как прежде | параметры запуска, зашитые в образ: точка входа, окружение, порт, проверка здоровья, рабочий каталог |
| метки основы целы | старые метки на месте, новые только `org.piqnyx.*` |
| сервер возьмёт наши файлы | изнутри образа, от пользователя 1001: файл читается, байткод от этого исходника, модуль грузится из нашего файла |

Лишний, пропавший или изменённый третий файл останавливает работу. Пустой список файлов -- тоже
остановка, а не «всё в порядке».

### Замена и откат (шаг 2.6, по слову Вита)

Решения Вита 29.09.2026: `pull_policy: never` -- да; сам возвращает прежний сервер, если новый не
стал здоровым за 3 минуты, -- да. Что скрипт делает до замены: сверяет, что в compose-файле и в
контейнере тот образ, на котором собран наш, и что сервер здоров; смотрит, нет ли архива сессии в
работе; ещё раз проверяет наш образ; сохраняет копию compose-файла
(`docker-compose.yml.before-piqnyx`) и журнал старого контейнера; спрашивает docker, годится ли
новый файл. Сервер останавливается только после этого.

В compose меняется строка образа; остальное как было: данные `../data/openviking`, шаблоны,
пользователь 1001, сеть host, адрес 127.0.0.1, запуск `--without-bot`, проверка здоровья, перезапуск,
срок остановки 30 с, ротация журнала.

Перед заменой -- копия compose-файла. Откат: вернуть копию, `docker compose down`, `docker compose
up -d`. Данные лежат на диске сервера отдельно от образа, формат хранения правка не трогает, старый
образ остаётся на диске.

К сведению: в compose сейчас метка `latest`, и `docker compose pull` молча сменил бы версию.

Предложение к шагу 2.6, решает Вит: рядом со строкой образа добавить `pull_policy: never`. Имя
`piqnyx/openviking` compose иначе может искать в общем реестре; с этой строкой он берёт образ только
с диска, а без образа на диске не стартует вовсе.
